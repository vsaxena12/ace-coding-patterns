# Design Pattern

## Tricks
Factory = create objects
Strategy = choose strategy based on behavior

## Strategy Pattern - Behavioral Patterns (Choose)

Strategy - One task which can be done in multiple ways.
- Example: Payment method type (Google Pay, Apple Pay, UPI, Credit)
- Interface -> [ConcreteClass1, ConcreteClass2, ConcreteClass3, .....]

### Use when
One task can be done in multiple ways.

### Problem it solves
Avoids large if-else / switch logic for behavior/algo changes. Strategy replaces conditional logic with polymorphism.

### Structure
- Strategy interface
- Concrete strategy classes
- Context class using strategy

### Common use cases
- Payment methods
- Discount calculation
- Pricing logic
- Sorting/filtering behavior

### Benefit
Easy to extend and swap behavior at runtime

## Factory (Get item)
Factory pattern - object creation depends on input, and we do not want new logic spread everywhere.

### Use when
Object creation depends on input/type.

### Problem it solves
Avoids scattered `new` and repeated if-else object creation logic.

### Structure
- Product interface
- Concrete product classes
- Factory class

### Common use cases
- Vehicle creation
- Payment method creation
- Notification creation

### Benefit
Centralizes object creation and reduces coupling
